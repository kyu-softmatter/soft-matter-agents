### I-20261022-office-02 -- does a user-interface frontend need the Claude Code CLI to talk to the sessions

- Said: 2026-10-22, in this window; read 00:02 -0700, twice in one
  message, the same words.
- Kind: a question about how the console (or any frontend) would connect
  to the sessions or agents. A design question; the plain-language part is
  answered below, the design part routed.

> 유저 인터페이스 프론트엔드랑 각 세션 또는 에이전트를 연결하려면 클로드 코드 cli룰 써야하나?

("To connect a user-interface frontend with each session or agent, do we
have to use the Claude Code CLI?")

What this seat answered from general knowledge, labelled as such: the CLI
is not the only way to drive a Claude session from a program -- the Claude
Agent SDK is the programmatic form of the same harness, and the console
already runs as its own server -- but what this repository allows is the
narrower question. Today the four agents run as separate Claude Code
sessions by decision (D11), sessions talk to each other only through file
cards and the librarian's read-only service (6.2), and the console drafts
plans and commands nothing (11-25); a frontend that reached into a session
would be a new channel beside those, which is the holders' to weigh and
the person's to decide.

   manager-console-office-20261017-1 (console/) for what the console does

   architecture-office-20261017-1 (plan.md 15, the runtime) for the stop

Sent ~00:08 -0700 after the record was written; the first commit of this
file, `6d9e8bc6`, followed. **All four answered by ~00:18 -0700**, each a
reading and not a design, none changing a file; passed to the person
together ~00:25 -0700, the 6.2 holder's Korean text as written. They agree
on the answer and divide the reasons:

- **architecture-20261007-1 (D11, 0.1).** The CLI program is not required,
  but what drives a session must be the Claude Code engine -- the CLI or
  the Agent SDK, the same engine with the same settings, hooks and tool
  connections. A frontend built straight on the model's API would not be a
  Claude Code session: no per-folder settings, denials, hooks or librarian
  connection, so a new kind of seat with no boundary, and one agent per
  session would mean nothing. A frontend that starts sessions is still "a
  session the person seated" on three conditions: one session per agent,
  started in that agent's own folder; the seating typed by the person in
  that session's own pane, since a seating typed by the frontend or
  another session is a relay and counts for nothing; and the frontend
  itself no seat and no tier. It would touch the cards-only rule (a second
  channel, so everything sent must be written to disk as sent) and the
  console's commands-nothing rule (steering conversations kept apart from
  anything that reaches a device).
- **architecture-office-20261017-1 (15, the runtime).** For the runtime,
  no: the part that runs the microscope has no Claude session in it, only
  Python running an approved plan, and everything a screen needs is
  already a file or a small local service -- the run's live event stream
  (one growing file per run, every command, reading, stop and the
  judgements' answers, its first line naming the stop channel and frame
  tap, its shape pinned in the shared rules), the stop channel (one
  message only), the frame tap (latest frame, commands nothing), and the
  records as files. Starting an approved plan is today a person's or a
  seat's act; a small local launcher accepting only "run plan X, revision
  N" against an approval on disk could fit the runtime's rules -- a design
  question for the person, not built. In one line: to watch, stop or (if
  added) start an approved run, no Claude Code is needed; it matters only
  for talking to the agents that design experiments or hold knowledge.
- **manager-console-office-20261017-1 (console/).** Nothing the console
  shows is a session: files read only (questions, plans, results,
  approvals, run records, the bridge's ledgers; a question submitted
  against real files is refused "not connected yet"), the runner's three
  local-only connections (stop channel, frame tap, a live-view host that
  starts only a person-approved list), the librarian not at all (no
  question, no identity, tools denied), and its own drafting assistant,
  which is not one of the four. The agents leave cards and the console
  reads them. A frontend talking to a session, against the console's four
  rules: a typed message passed to a session is a relayed instruction, not
  in the session's window and not a card; a frontend telling the
  microscope's sessions to act is a second command path with a model as
  decider, the path the cut just removed; a chat link leaves no card, so
  what a session says has no source and no grade. What fits: a frontend
  that shows what the sessions wrote, and the person speaking in a
  session's own window or through the intake. Nothing in the console needs
  the CLI or any session.
- **architecture-20261003-1 (6.2).** Not the CLI necessarily: a program
  reaches a session three ways -- the CLI's non-interactive mode, the
  Agent SDK, or no live link at all, the screen reading and writing the
  files sessions already read. 6.2 rule 2 already covers it: a message may
  notify and may not be the only copy, so a frontend's message into a
  session is allowed as notification and becomes a refused channel the
  moment something exists only in it. To be allowed: (a) a trace, every
  word carried appended verbatim on disk with session, time and direction,
  or pointers to files only; (b) a boundary, writing no agent's directory;
  (c) no authority -- it cannot seat, cannot widen a permission, and no
  approval, hash signature, safety value or bench hand-over is made by a
  click alone; (d) no instrument path. A plain program needs no seat; a
  routing model of its own would be a seat the person seats. Two front
  doors already exist, the intake desk for the person's words and the
  console for reading state and drafting plans; a frontend wired to every
  session would put a second window beside the intake and lose its record.
  The direction consistent with 6, if one screen is wanted: a console
  screen that carries the person's words to the intake seat, which records
  them as now -- a direction, not a design.

What the person does with this is theirs: nothing is decided, and no
holder proposed a change until the person says what the screen is for.
