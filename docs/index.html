The loop

One question, all the way around

Most lab automation stops at execution: a human decides the conditions and the software moves the stage. This system closes the other half of the circle — the planning, the observation and the knowledge are inside the loop too, so what a run teaches becomes the input to the next question rather than a note in someone's file.

On the bench

Autonomous acquisition, on a real microscope

The instrument half is not a simulation of a lab. The agent emits an acquisition that deterministic code has already checked against what the sample and the hardware will survive, and a human approves it before anything moves.

The system

Four agents, one knowledge store

Two agents execute: one against a bench, one against an engine. They never reference each other directly — everything between them crosses a bridge that is forbidden to author anything. Neither keeps its own facts; the librarian is the only knowledge store, and it records what it could not answer as carefully as what it could.

Microscope agent

Turns a measurement question into an instrument configuration and an acquisition that is detectable, sufficient, and inside what the sample and the hardware will survive — then runs it under approval.

executes · against a bench

Simulation agent

Same five stages, a different axis list. Turns a computational question into a parameter set that is stable, sampled correctly and inside budget. The cheapest simulation is the one it decides not to run.

executes · against an engine

Librarian

Owns every fact the other three use, and records what it could not answer. Nobody checked and checked and it is not there are different claims, and only one of them means go and find it.

knowledge · read-only

Bridge

Carries a card from one executing agent to the other and keeps track of whose turn it is. It adds no number, rounds nothing off, improves no condition. A courier that edits the parcel is not a courier.

transport · authors nothing

What holds it together

The hard part is not the proposal. It is the gate.

A model proposing settings is easy and not worth much. What makes a proposal usable is that it has to survive deterministic code before it becomes a plan.

01

Every number carries its evidence

A value is value, unit, source, grade — and the grade is derived from the source, never self-reported. A number a model invented has a name, and it may not enter a plan or the knowledge base.

02

Safety is decided by code

Never by a model. People first, then instruments, then samples and data. Where the evidence is ambiguous the system stops instead of proceeding.

03

A refusal is a result

When the evidence for a value does not exist, the system says so — with where it looked — instead of inventing one. The gap is an output, recorded and reusable.

Status

Under active construction, in the open

The card contracts and the deterministic gate are in place, the knowledge service answers, and the four agents are being built concurrently rather than in sequence. Nothing here quotes a progress number: the repository's own rule is that a count written into prose is wrong by the next day, so the honest answer is the one you get by running the validator. The design document is authoritative, long, and in Korean.
